Основная цель: сделать централизованную, расширяемую и безопасную систему окон, которая управляет порядком открытия/закрытия UI, обработкой Esc, вложенными окнами, модальными окнами, контекстными меню, блокировкой игрового ввода, курсором и паузой игры.

Код нужно писать с учётом:

* MVVM-архитектуры, где это уместно.
* SOLID-принципов.
* R3 для реактивных событий/состояний, если это уместно.

Нужна система по принципу стека окон:

* Если открывается окно, оно добавляется в стек.
* Если нажимается Esc, закрывается верхнее окно в стеке.
* Если стек пустой и нажимается Esc в gameplay-сцене, открывается меню паузы.
* Если окно является дочерним/вложенным, Esc закрывает только его, а родительское окно остаётся открытым.
* Если закрывается родительское окно, все дочерние/открытые поверх него окна должны закрыться тоже.
* Порядок закрытия должен быть строго LIFO: последним открылось — первым закрылось.
* Модальное окно должно блокировать взаимодействие с окнами под ним, но при Esc закрываться первым.
* Context Menu должно закрываться как обычное верхнее окно в стеке.
* Tooltip/hover-подсказки не должны считаться полноценными окнами, если они не требуют участия в Esc-стеке.

Пример ожидаемого поведения:

1. Игрок открыл инвентарь.
2. Открыл окно осмотра предмета.
3. Нажал Esc — закрылось окно осмотра предмета.
4. Нажал Esc ещё раз — закрылся инвентарь.
5. Нажал Esc ещё раз — открылось меню паузы.
6. В меню паузы игрок открыл настройки.
7. Нажал Esc — настройки закрылись, игрок вернулся в меню паузы.
8. Нажал Esc ещё раз — меню паузы закрылось.

Нужно предусмотреть разные типы окон:

* Root Window — корневое окно: Inventory, Pause Menu, Main Menu.
* Sub Window — дочернее окно: Options, Save/Load, Item Info.
* Popup/Modal — модальное окно: Exit Modal, Split Stack, Confirm Dialog.
* Context Menu — контекстное меню, например ПКМ по предмету.

* Нужно проверить существующую архитектуру паузы и встроиться аккуратно.
* Если отдельной системы паузы нет, сделать аккуратный сервис/контроллер паузы, который можно будет заменить позже.

Gameplay input:

* Когда открыто UI-окно, которое блокирует управление, игровой ввод должен быть заблокирован.
* При закрытии всех блокирующих окон игровой ввод должен восстановиться.
* Нельзя завязываться на хаотичные проверки в разных местах.
* Управление блокировкой должно быть централизованным.

Cursor:

* Если открыто окно, требующее курсор, курсор должен быть видимым и разблокированным.
* Если UI закрыт и gameplay input активен, курсор должен вернуться в gameplay-состояние.
* Управление курсором должно быть централизованным.

Важно:

* Логика Esc не должна быть размазана по разным окнам.
* Центральная система должна решать, какое окно закрыть или открыть.
* Окна могут иметь свои callback-и/команды, но порядок управления должен контролировать общий Window Manager / Navigation Service.
* Один Esc — одно действие.
* Нельзя, чтобы один Esc одновременно закрывал дочернее окно и открывал меню паузы.
* Нельзя, чтобы после закрытия последнего окна в тот же кадр сразу открывалась пауза, если Esc был использован именно для закрытия окна.
* Pause Menu открывается по Esc только если до обработки Esc стек был пустой.

* Tab отвечает только за открытие/закрытие Inventory Panel через новую систему.
* ПКМ по предмету отвечает только за открытие Inventory Item Context Menu через новую систему.
* Кнопка “Осмотреть” отвечает только за открытие Item Info Panel через новую систему.
* Esc отвечает только за Back-действие в Window Manager / UI Navigation Service.
* Никакие окна не должны самостоятельно решать глобальный порядок закрытия.
* Никакие отдельные скрипты не должны напрямую закрывать другие окна в обход Window Manager, кроме случаев, когда это явно оформлено как команда навигации через общий сервис.

Нужно сохранить существующую пользовательскую логику инвентаря:

* Не сломать выбор предмета.
* Не сломать передачу данных предмета в Item Info Panel.
* Не сломать позиционирование Inventory Item Context Menu.
* Не сломать логику Count Drag Window.
* Не сломать кнопки контекстного меню.
* Не сломать текущую работу Inventory Panel по Tab.

Но вся навигация открытия/закрытия этих окон должна быть приведена к новой централизованной системе.

Нужен итоговый результат:

* Чистая система управления окнами.
* Предсказуемое поведение Esc.
* Корректная работа gameplay-сцены Test.unity.
* Корректная работа MainMenu.unity.
* Централизованное управление UI navigation.
* Возможность расширять систему новыми окнами без переписывания Esc-логики.
* Код должен быть понятный, аккуратный, без дублирования и без хаотичных условий.

В конце работы выдать summary:

* Какие файлы изменены.

* Как теперь работает Esc.

* Какие риски или ограничения остались.

* Что именно было удалено или перенаправлено.
* Где теперь обрабатывается Esc.
